## 发现并修复的问题

## 响应速度与使用体验

首轮四十道业务任务从提交到完整报告的中位数 **14.029 秒**，P95 **36.651 秒**，范围 **4.807–68.178 秒**，包含队列、远程模型、工具及落库。此统计也包含首轮失败任务的结束时间，不是首字延迟或服务 SLA。

最慢题为新分布的品类 Python 分析：SQL 两次、Python、绘图合计约 2.5 秒；六次远程模型请求合计约 62 秒，其中一轮约 29.7 秒。一个无依据说明数字被拦截后修正。响应主要受多轮模型调用与错误修正影响，扩大数据库并不能直接解决这些等待。

详情 API 二十次、四路并发，中位数 0.202 秒，P95 0.217 秒。两个并发分析均正确，但不足以代表多人生产并发性能。

真实摘要将构造的超预算历史从估计 16,293 tokens 压缩至 475，输入预算 3,635；当前问题和原始历史保留。该次摘要调用 9.116 秒。估算不是模型精确 tokenizer，摘要也可能丢细节。

月份/说明修复后的同题两次真实复测都成功，但分别耗时 43.977 和 33.877 秒；第一题出现多次不支持函数和 SQL 纠错。加入 LAG/LEAD 后两次仍耗时 39.717/40.550 秒，工具与校验错误由十二次降到四次，但没有证明延迟改善。补充核对还发现这两份报告的一个中间表把订单环比写成 0%，最后一张改成 -20%。原来的目标列评分没有覆盖自发增加的比例列，所以不能称两份报告全部正确。

该问题记录于 `supplemental-review.json`。随后统一数值除法，并在最后的 `acceptance-numeric-retest-20261010` 同题复测中同时检查目标字段及报告所有已识别派生指标。每一轮原始记录保留，不能用重测替换首轮失败或宣称已建立稳定速度提升。

最后两次实测耗时 22.218/35.096 秒，中位数 28.657 秒，均交付完整正确的目标结果、图表和已识别的补充差值/比例。样本仅两次，模型等待存在波动，无法据此证明普遍的性能提升。

## 作为简历项目的判断与边界

可以作为智能体应用开发项目：它具备模型自主工具选择、工具错误反馈、人工介入恢复、持久任务、受限执行、用户隔离、可追溯产物、长期记忆和可验证的数值评测。相比项目一的固定书籍 RAG 流程，能展示不同的工程能力。

当前定位应是电商四表场景的智能体项目原型。全部数据为明确标注的合成数据；未使用完整真实 Olist 或企业脱敏数据，未验证任意 Excel、复杂未知业务问题、多人长期运行、不同模型、大规模并发、完整计费或操作系统级崩溃演练。现有 checkpoint 故障恢复测试是受控数据库状态模拟。

数字可追溯不能保证任意 SQL 的业务语义或自然语言判断正确；本次整体表现中的“规模中等、客单价较高”缺少外部比较基准，已加强提示约束，仍需要人工审阅。报告保留中间表，其他类型的错误中间结果仍可能随最终正确结果一并展示；当前未建立通用的产物撤销与语义判定机制。说明降级时会明确提示，不应把降级报告宣称为完成了复杂原因解释。

本轮浏览器安全策略拦截了打开本地页面，真实浏览器交互验收未完成；前端只完成渲染安全、表格完整性、语法检查及源码检查。旧截图不是本轮浏览器验证证据。无法宣称项目没有任何 bug。

运行链路与数值基准在现有环境可复现；未从全新环境重新安装验证。远程模型与容器标签可能变化，输出措辞、工具路径和耗时不能逐字逐秒复现。本地结果目录被 Git 忽略，分享项目时需另行附脱敏评测摘要和必要证据。

下一步最有价值的是用一份脱敏真实数据与更多自然问题扩充独立基准，再验证浏览器完整流程及持续并发。简历可如实写：

> 基于 FastAPI、LangGraph、PostgreSQL、Celery 与 Milvus 构建电商数据分析智能体，实现 SQL/Python/绘图自主调用、任务持久恢复及个性化记忆；建立独立数值验收，在四十道合成数据业务任务中首轮成功交付三十九道，定位并修复状态竞争、偏好作用域及报告核验问题。
